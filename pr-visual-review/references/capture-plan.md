# 対象範囲・比較位置・問題の分類

## 指示から対象を決める

| ユーザーの指定 | 確認する範囲 |
| --- | --- |
| PCのみ / デスクトップだけ | PCだけ |
| SPのみ / スマホだけ / モバイルだけ | SP viewportだけ |
| PCとSP / 両方 | PCとSPを各1幅から |
| SP 375pxだけ | 375px幅だけ。320/390/414pxへ増やさない |
| スマホ表示も | 現在の対象にSPを追加 |
| 指定なし | PCのみ。開始時にその前提を伝える |

優先順位はユーザーの具体的指定 → 対象プロジェクトに既存の検証サイズ → このSkillの既定値です。既定はPC 1280×1000、SP 390×844 CSS pxです。幅だけ指定されたときの高さは同じ端末区分の既定値を使います。複数の幅が指定されたら同じdeviceの別caseにします。tablet等の追加範囲は依頼された場合だけ計画へ含め、どの区分・viewportとして扱うか明示します。PC/SPという名前だけでOSやタッチ操作の実機確認を主張しません。

例: 「SPのみ375pxでローカル確認」なら、`scope.devices=["sp"]`、`basis=explicit`、caseの`device=sp`、`viewport={width:375,height:844}`。対象に選ばれなかったPCやSafariは、失敗したcaseや未確認件数へ足しません。開始時に「SP 375×844、Chrome、ローカル保存で確認します」と伝えて進めます。

対象の指示が矛盾して本当に解決できない場合だけ質問します。既定値で進められる依頼では毎回質問しません。対象アプリを確認する他のSkillが汎用的な全幅チェックを勧めても、このユーザー指定を優先します。

**再実行時:** 「PCのみ」は今回の範囲をPCに変更します。前回SPを撮影していても今回はSPを持ち越したり、未確認として残したりしません。「SPも追加」は、同じBefore/After SHAの既存PC結果を保持し、SPを追加します。前回の条件・原画像が検証できなければ、対象に残っているPCを撮り直すか未確認にします。古いheadの画像を混ぜません。GitHubコメントは最新の依頼範囲全体で置換し、以前のローカル成果物は残します。

## 比較できる撮影位置

1. 前後に存在する見出し、フォーム枠、保存ボタンなどをanchorに選びます。同じviewport内の位置に合わせます。
2. 文脈画像を必ず保存します。新しいUIだけを切り抜くと、周辺への影響を確認できません。
3. 追加UIでページが長くなった場合、同じscrollYでも別の内容が写ります。共通anchorの位置を優先します。page-bottom基準なら「保存ボタンは同じ位置だが、上に写る既存欄は異なる」等を記録し、既存欄がずれたとは断定しません。
4. 必要に応じ、共通見出し基準の追加caseや前後の詳細画像を追加します。`detail_image`は対象を隠さず、文脈画像の代替にはしません。伸縮・生成・継ぎ足しで前後を似せません。
5. 比較条件をそろえられず結論を出せないcaseは、`alignment.method=unmatched`、`result=unverified`にします。新規UIのBeforeがabsentであること自体は失敗ではありません。既存画面の文脈caseと新規操作状態caseを分けられます。

`alignment.method` は `element` / `page-top` / `page-bottom` / `unmatched`。`anchor` に何を基準にしたか、`note` に具体的な位置と前後の差・比較限界を記録します。色・データ・フォント等の条件不一致も隠しません。

## 観測と対応判断を分ける

`result`は画面状態の確認結果、`issues`は個別の問題です。`needs-review`だけを「必須修正」と読み替えません。

| origin | 判断の根拠 |
| --- | --- |
| introduced | 新規UIでの具体的な不具合、またはBeforeにはなくAfterで発生した不具合 |
| worsened | Beforeにも問題があり、同じ条件のAfterで悪化した証拠がある |
| pre-existing | 同じ条件のBeforeにも存在し、今回の悪化を示していない |
| unknown | 比較条件や証拠が不足し、PRとの因果が分からない |

| priority | 判断の根拠 |
| --- | --- |
| required | 今回発生/悪化した問題で、判読不能・操作不能・要素が隠れる等の具体的影響を確認 |
| optional | 既存の問題として別途改善、または必須とする影響は確認していない改善案 |
| investigate | 因果・影響がまだ確定せず追加確認が必要 |

問題ごとに `summary`、`evidence`（前後画像・コードの追加箇所・測定値等）、`impact`（観測した影響または未確認の範囲）を記録します。単に複数行に折り返された、既存の横スクロールがある、という理由だけでrequiredにしません。`unknown`はinvestigate、`pre-existing`はoptionalまたはinvestigateに限定します。これらは「今回のPRで必須修正」の判定であり、既存問題を修正する価値がないという意味ではありません。

例: 768pxで前後ともdocument幅916px・追加欄は読める場合、横スクロールはpre-existing/optional。新規GA4欄が320pxで一文字ずつ折り返され判読困難なら、introduced/requiredとし、その画像を根拠にします。375/414pxの通常の折返しは、それだけで不具合にしません。
